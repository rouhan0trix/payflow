POST

/api/payments

Creates a new payment record or safely replays an existing request if the idempotency key matches.

Request Payload Specification

  • amount_paise (integer, required): Positive integer in minor units (e.g. 25000 for ₹250.00). Floats, negatives, strings, and booleans are rejected.
  • currency (string, optional): Defaults to "INR".
  • description (string, required): Non-empty string, maximum 255 characters.
  • idempotency_key (string, required): Unique client-generated key, maximum 64 characters.
  • simulate_status (string, optional): Demo parameter: "succeeded" (default), "failed", or "pending".

Sample cURL Command

curl -X POST http://127.0.0.1:5000/api/payments \
  -H "Content-Type: application/json" \
  -d '{
    "amount_paise": 25000,
    "currency": "INR",
    "description": "Order #1024 - Annual Plan",
    "idempotency_key": "order-1024-client-token"
  }'

POST

/api/payments/<id>/refund

Issues a full simulated refund. Wrapped in an ACID database transaction.

Behavior & State Guards

  • HTTP 200: Payment is succeeded and was not previously refunded. Returns updated payment with embedded refund object.
  • HTTP 404: Payment ID does not exist.
  • HTTP 409: Payment is in an ineligible state (already refunded, failed, or pending).

Sample Response (HTTP 200 OK)

{
  "message": "Refund processed successfully.",
  "payment": {
    "id": "pay_a94f6c12b73e8901",
    "amount_paise": 25000,
    "status": "refunded",
    "refund": {
      "id": "rf_81b2e4f0d3a9c71e",
      "payment_id": "pay_a94f6c12b73e8901",
      "amount_paise": 25000,
      "formatted_amount_inr": "250.00",
      "created_at": "2026-09-29T10:05:00+00:00"
    }
  }
}
🎯 INTERVIEW READY

60–90 Second Interview Elevator Pitch

A natural, high-impact script you can speak verbatim when an interviewer asks: "Walk me through this project."

“PayFlow is a simulated payment processing and transaction ledger platform I built using Python Flask, SQLite, and vanilla JavaScript. Rather than just basic CRUD, I designed it around real fintech reliability patterns.

First, I implemented idempotency keys to prevent double-charging: if a client retries a payment with the same key and payload, the server returns the existing transaction with an HTTP 200 replay; if the payload differs, it catches the conflict with an HTTP 409.

Second, to avoid floating-point rounding errors common with decimal currencies, all amounts are validated and stored as integer minor units (paise).

Third, for refunds, I implemented a strict state machine: only succeeded payments can be refunded, exactly once. The refund record creation, status update, and audit log write are bound inside an atomic database transaction with automatic rollback on failure.

I also wrote an automated test suite covering duplicate requests, state violations, and SQL injection defense.”

Core Interview Questions & Detailed Answers

Deep technical explanations for common interview follow-ups.

1. What is idempotency and how is it implemented here?

Concept: An operation is idempotent if performing it multiple times has the exact same outcome as performing it once. In payment gateways, network drops or impatient users can trigger duplicate POST requests.

Implementation: The client sends a unique idempotency_key. Before inserting, the backend queries SQLite for that key.

  • If the key exists and the payload (amount, currency, description) matches: the server replays the existing record with HTTP 200 OK and is_replay: true without inserting anything.
  • If the key exists but the payload was modified: the server returns HTTP 409 Conflict because reusing a token with different parameters violates protocol integrity.
  • If the key is new: it executes an insert within a database transaction.

2. Why store paise as integers instead of floating-point rupees?

Standard IEEE 754 floating-point arithmetic cannot represent decimal fractions precisely in binary (for example, in Python: 0.1 + 0.2 == 0.30000000000000004). Over thousands of financial transactions, rounding errors compound into discrepancies.

By storing ₹1.00 as 100 integer paise, all additions, subtractions, and aggregations are 100% exact integer operations. Formatting to rupees is done strictly in the presentation layer.

3. Why use a database transaction for refunds?

A refund requires three distinct writes:

  1. Inserting a row into refunds
  2. Updating the payment row status to refunded
  3. Inserting an audit record into status_history

If step 1 succeeds but the server crashes before step 2, the system ends up in a corrupt state where a refund exists but the payment remains marked succeeded. Using Python’s context manager (with db:) ensures Atomicity: all three writes commit together, or none of them do.

4. Why SQLite for this project? How would you scale to production?

SQLite is embedded, zero-configuration, and runs in-process, making it ideal for self-contained demonstrations and local unit testing.

Production Roadmap: For high-concurrency production:

  • Migrate to PostgreSQL with row-level locking (SELECT FOR UPDATE) or optimistic locking.
  • Use Redis with TTL for distributed idempotency locks.
  • Add merchant multi-tenancy with compound unique keys: (merchant_id, idempotency_key).
  • Add webhook signature verification (HMAC-SHA256).
